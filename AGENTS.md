# Base44 development notes

- This is browser-only: no API, database, or external credentials. Camera access needs browser permission; without it the app intentionally runs an animated ambient simulation.
- Base44 Compose builds the Rust/WASM from mounted source before starting Vite on host port 3000. The Node container deliberately has no Rust toolchain: its `npm run dev` skips the already-built artifact. Do not remove that WASM output while the web service is running; rebuild through the `wasm` service instead.
- `scripts/base44-wasm.sh` installs a cached wasm-pack, builds on each service start, and polls Rust sources/manifests for rebuilds. Build output, npm dependencies, vendored MediaPipe runtime, and downloaded models are generated/ignored, not committed.
- Two WASM builds: `web/src/wasm` (baseline) and `web/src/wasm-mt` (rayon + Web Workers, nightly `-Zbuild-std`, own target dir `target/wasm-mt`). The threaded link must export `__wasm_init_tls`/`__tls_*` explicitly (done in `scripts/build-wasm.sh`) or wasm-bindgen fails with "failed to find `__wasm_init_tls`". `scripts/base44-wasm.sh` is read once at container start — restart the `wasm` service after editing it.
- The preview proxy forwards `Cross-Origin-Opener-Policy` but strips `Cross-Origin-Embedder-Policy`, so Vite's headers alone never produce isolation. `web/public/coi-serviceworker.js` + `web/src/cross-origin-isolation.ts` re-attach both from a Service Worker and reload once; that runs only at top level, so the embedded iframe stays single-threaded by design. Verify the threaded engine in a standalone port-3000 tab (hard-reload once so the worker installs) via `window.__aether.diagnostics().engine`.
- MediaPipe inference runs in `web/src/perception.worker.ts` (module worker), driven by `ImageBitmap`s; `perception-worker-client.ts` is the `PerceptionSource` the app uses, with inline `MediaPipePerception` as fallback. Two non-obvious requirements: a module worker's inherited `importScripts` exists but throws, so `worker-import-scripts.ts` must override it via `Object.defineProperty` + indirect eval or the runtime fails with "ModuleFactory not set"; and Vite tags dynamic imports with `?import`, which its transform pipeline refuses for `public/` files — the `aether:mp-wasm-as-asset` plugin in `vite.config.ts` strips that query. A classic worker would avoid both but `worker.format` is per-project and the rayon threads need `es`.
- `web/src/performance-governor.ts` adapts quality at runtime from the smoothed fps: internal resolution (`Renderer.setQualityScale`), `pressure_iters`, then pool size. Tier 0 is the user's own settings, it is paused during overdrive, and HUD pool changes rebase it. Read `window.__aether.diagnostics().qualityTier`. The embedded preview iframe does run the loop and the governor whenever it is visible — and stops dead at `frames: 0` when it is hidden, which is why it can look like it never gets an animation frame — but always single-threaded (`SharedArrayBuffer unavailable`), so it settles at a degraded tier that says nothing about real performance — judge frame rate only in a standalone port-3000 tab.
- Vite uses polling and Compose passes the platform's `__VITE_ADDITIONAL_SERVER_ALLOWED_HOSTS` for rotating preview hosts. The CLI binds 0.0.0.0 without changing the normal localhost default.
- `crates/aether-core/src/visual.rs` measures the visual qualities tuning changes (dye saturation at the tone ceiling, structure/filament contrast, swirl, coverage, projection residual) from the dye grids, so a parameter change can be judged without a browser. `contrast` is normalised by brightness on purpose — it must stay a structure measure, not an exposure one — and `divergence` is an absolute residual that scales with drive strength, so compare it against `max_speed`, never a fixed number. Its tests pin `Params::default` against both failure modes: blown-out white frame and swirl-free flat field.
- `web/src/qa-recorder.ts` is how a manual QA pass leaves evidence: the frame loop feeds it diagnostics, it keeps a bounded summary (fps percentiles, step/render/inference/camera/hud times, quality-tier and perception transitions). It also records `engineReason` and `crossOriginIsolated`, so a `single:1` session says which gate rejected the threaded build instead of leaving it to guesswork. `frameMs` is the whole callback and `outsideMs` is the wall-clock gap it did not spend, which is the row that matters when the measured work sums far under the frame period: that time is GPU work completing after the GL calls return, compositing, or another task holding the loop.
- Reading a QA session from outside the tab goes over HTTP, not storage: `curl localhost:3000/__qa/session`, served by the `aether:qa-session-endpoint` plugin (`web/qa-session-endpoint.ts`), which holds the newest posted record in dev-server memory. `localStorage` is **not** a usable bridge — Chrome partitions it by top-level site, so the embedded preview iframe gets its own bucket and can never read a standalone tab's record even though the origin is identical; a whole debugging round was lost to reading the iframe's own numbers back and believing they were the user's. The recorder still writes storage for in-tab reads (`window.__aether.lastQaSession()`) and `sendBeacon`s the same summary to the endpoint, and it uploads/persists only from a top-level document so the iframe's own throttled single-threaded record cannot overwrite a real session.
- CI (`.github/workflows/ci.yml`) runs `cargo fmt --check`, `cargo clippy --workspace --all-targets -D warnings`, `cargo test --workspace`, then **both** WASM builds + `npm run typecheck` + `npm run test:unit` (vitest). Two things CI is fussy about: the toolchain actions must pin `1.90.0` (the same channel as `rust-toolchain.toml`, or the pinned toolchain ends up without rustfmt/clippy and `cargo fmt` fails with exit 1), and the threaded build must run there too because the typecheck follows `engine-loader.ts`'s dynamic import into `web/src/wasm-mt`. Run fmt/clippy in the `wasm` container before pushing; the two `needless_range_loop` allows in `fluid/` are deliberate (the loop index also builds the flat grid index).
- Verify with `docker compose -f docker-compose.base44.yml ps`, `curl -f http://localhost:3000/`, `docker compose -f docker-compose.base44.yml exec -T wasm cargo test --workspace`, and `docker compose -f docker-compose.base44.yml exec -T web npm run typecheck`.
- Browser readiness: `#boot.done` is intentionally invisible, so wait for attachment, not visibility. Read `window.__aether.diagnostics()` for advancing frames and camera/perception status. A canvas screenshot confirms actual rendering; a populated DOM alone does not.
- Initial setup verified native workspace tests, TypeScript checking, live source serving, and the preview rendering in ambient mode. Real webcam gesture recognition requires camera permission and was not verified during setup.
- The gesture tutorial is a *mode*: `web/src/tutorial.ts` (full-screen cinematic stage + timing), `web/src/tutorial-steps.ts` (step order + how-to lines) and `web/src/hand-art.ts` (each pose is two stacked glyphs — rest and the taught pose — cross-fading on a CSS loop so the card shows the movement, with a charge ring around the tile fed by `--vn` from `setCharge`) over `web/src/hand-icons.ts` (hand glyphs vendored from Fluent Emoji high contrast, MIT, as path data — generating hand shapes from finger declarations was tried twice and never read as a hand, so do not go back to it). Opening it (T, or the panel's book button) dims the stage with `.tut-scrim` and calls `HudCallbacks.onPractice` → `AetherEngine.set_practice(true)`, which keeps single gestures casting but suppresses combos and duets — that, not a pause between steps, is what stops the lesson chaining poses into nova/tempest/supernova. A step passes after the spell is latched for `HOLD_MS`, except `release`, which passes on sight because it is a one-frame report. It auto-starts the first time `HANDS_PRESENT > 0` and remembers completion/dismissal in `localStorage` (`aether.tutorial.done`) — clear that key to see the auto-start again. `web/src/hand-mirror.ts` draws the caster's own skeleton from the packed hand buffer (`HudStats.hands`, passed through `hud.ts`) inside the charge ring — and *is* the hold timer: a second accent-blue copy of the same polylines, clipped by a rect that rises from the wrist as `setCharge` feeds it, replaced the taught `hand-art` glyph on the step card, x flipped for the mirrored stage and fitted into `ICON_BOX` so distance from the camera doesn't change its size; it needs a camera, so it stays invisible in the embedded preview. The target pose beside it comes from `web/src/pose-landmarks.ts`: most poses are generated from per-finger direction/curl/segment declarations, but the fist (`attract`) and thumbs-up (`shatter`) are *traced* literal landmark tables, because those hands are seen from the side and the front-view finger model could not read as either. `pose-landmarks.test.ts` pins the recognisable features. `TutorialProgress` is the DOM-free step logic covered by `tutorial.test.ts`. It can't be walked with real gestures inside the embedded preview (no camera); "next" skips a step for manual checks. The HUD's static `shots` section in `hud-combos.ts` lists the thrown bolt only — the finger gun and its aim sight were removed.
- `Release` (opening a fist held ≥ `RELEASE_MIN_CHARGE`) is reported by `spells.rs` only and is never latched by the tracker.
- Two-hand duets live in `crates/aether-core/src/duet/` (tide = fist + palm, clap = open hands meeting fast, big bang = two fists squeezed then both opened). Its distances are in hand widths, not normalised units, and a fist is excluded from the clap so squeezing for the big bang never claps. The HUD reads them via `duet_book()` / `duet_progress()` and renders them as a second section of `hud-combos.ts`; a duet step is `spell+spell` (both hands) or a motion word shown verbatim.
- Energy bolts are thrown, not clicked: `crates/aether-core/src/bolt/` reads palm velocity in hand widths per second and a fast flick of an open hand (a fist is excluded) hurls a cyan streak from the palm along the motion; a push *at* the camera has no on-screen motion, so it is read from the hand's scale growing fast (smoothed relative growth per second) and detonates at the palm instead (`dir == [0, 0]`). That reading is deliberately hard to trip — a high `THROW_GROWTH` plus a requirement that the palm be moving slower than `THROW_SPEED` across the frame — because a hand wandering around the frame changes apparent depth constantly and anything looser turned most throws into camera pushes. One flick is one bolt — it re-arms only after the hand slows, so reversing direction is deliberately a new throw. The engine fires it inside `step`, after the spell layer.
- Gesture latency has two ceilings that look like nothing from the outside. MediaPipe's duty-cycle limiter in `perception.ts` (`BUDGET_MS`/`MAX_DUTY`) exists only to keep a synchronous inference from stalling the render loop, so `perception.worker.ts` constructs it with `rationInference: false` — left on there it inserts idle time between landmarks (~16 Hz down to ~6 Hz at a 60 ms pass) while blocking nobody. And the camera is opened with `frameRate: { ideal: 60 }`: perception submits a frame only when `video.currentTime` advances, so the capture rate is a hard floor on how soon a gesture can be seen, however fast inference is.
- The renderer has two backends behind `SceneRenderer` (`web/src/types.ts`): the WebGL2 compositor (`web/src/render/`) and a WebGPU one (`web/src/gpu/`) that also *simulates* the particles in a compute pass. `web/src/gpu/index.ts` picks one at boot — WebGPU only on a hardware adapter, since a software one (SwiftShader) is slower than the WebGL2 path it replaces; `?gpu=off` / `?gpu=on` override the gate, and `window.__aether.diagnostics().renderBackend` says which won. The look table is shared (`web/src/render/styles.ts`), so the two chains differ in API, never in grade. WGSL is y-down and intermediates are `rgba16float`, so there is no `v` flip and no 8-bit encode/decode contract.
- On the WebGPU path the engine hands the pool over (`AetherEngine.set_gpu_particles`): the Rust pool stops advancing, every spell mutation is appended to the per-frame op log (`crates/aether-core/src/particles/offload.rs`; `OP_KINDS` there is the protocol's single source — `particle_op_layout()` publishes `[stride, max, ...kinds]`, `assertOpLayout` in `constants.ts` compares `PARTICLE_OP` against it entry by entry at boot, and `gpu/shaders/particles.ts` generates its WGSL `OP_*` constants from `PARTICLE_OP`, pinned by `op-protocol.test.ts`; add a kind in Rust and TS together or the boot fails naming it), and the compute shader replays that log per particle before integrating, so both backends see the same sequence. Randomness cannot match bit-for-bit (a PCG hash of particle/frame/salt replaces the per-lane xoshiro stream) — compare the two statistically, never frame-by-frame. `particlesAlive()` and `sampleLuminance()` come back through asynchronous map reads and are a frame behind by design; stalling the queue for them would cost more than they are worth.
- A WebGPU submission that touches a buffer which is mapped or has a map pending is dropped *entirely* by the driver, with no exception thrown — the tab just misses that frame, and intermittently that is exactly what "the screen flickers" is. That rule now lives in one place, `gpu/readback.ts`: ask `idle` before encoding the copy, call `poll` after the submit. Never hand-roll a staging buffer plus a pending flag again — that duplication is what let the counter copy forget the rule while the probe copy kept it. The fault was found only through `device.onuncapturederror` → `gpu/error-log.ts` → the QA session (`x343 [Buffer "counters-read"] used in submit while mapped`), so keep that chain intact.
- `gpu/` is split by lifetime, not by tidiness: `particle-sim.ts` owns the pool, the fluid/obstacle/op buffers and both compute entry points, while `renderer.ts` owns targets, draws and the post chain — with the post chain's two self-contained pieces pulled out beside it: `target.ts` (the resized-in-place colour target plus the `FullscreenPass` shape the renderer hands down), `bloom.ts` (`BloomChain`: its own ladder targets, uniforms and binds; `resize`/`buildBinds`/`record`) `probe.ts` (`LuminanceProbe`: the 16x16 reduction, its `Readback` and the mean-luminance reduce) and `overlay.ts` (`HandOverlay`: the hand skeleton — the chain's only vertex buffer, both uniform buffers and their binds; `record(encoder, target, hands, strength, pointScale)`. Two uniform buffers and two passes are deliberate: a `writeBuffer` lands before the submit, so reusing one buffer would retroactively change the line draw). The renderer's two construction-time halves are out of it as well: `pipelines.ts` (`HDR_FORMAT`, the additive blend and `createPipelines` — every render pipeline as one record, built from shader source alone, so the renderer only ever asks them for a bind group layout) and `sources.ts` (`SceneSources`: the dye/debug/noise/camera textures, the three shared samplers and the two uploads). The camera texture is the one input that is reallocated at runtime, so it follows the pool's rule — `SceneSources.version` bumps and only that may invalidate the bind groups over those views. The renderer draws straight from `sim.pool`, so it rebuilds its draw bind group off `sim.poolVersion` — a pool or obstacle realloc bumps that, and nothing else may be used to detect it. The per-frame arithmetic that must match `aether_core::particles` (dt folds, decays, the carried fractional respawn budget) is the pure `gpu/sim-uniform.ts`, whose test pins the WGSL `Sim` slot order — change the shader struct and change that test together.
- `gpu/shaders/particles.ts` is now an index: the doc explaining the CPU-parity contract, randomness and respawn budget, plus re-exports. `particles-layout.ts` holds the byte/dispatch constants and the generated `OP_KINDS_WGSL`, `particles-compute.ts` the op-log replay and both compute entry points, `particles-draw.ts` the instanced quad. The two halves import the *layout* module, never the index — importing the index made a cycle that left the spliced op constants `undefined` while typecheck stayed green, which only `op-protocol.test.ts` caught.
- WGSL is unit-tested without a GPU: `gpu/shaders/shaders.test.ts` parses every module with `wgsl_reflect` and pins what a driver would only reject on someone else's hardware — syntax, `*_UNIFORM_FLOATS * 4` against each uniform struct's reflected size (the renderer sizes its buffers from those same constants, never a literal), the compute kernel's seven bindings and their access modes against `ParticleSim`'s explicit layout, `workgroup_size` against `STEP_WORKGROUP`, and the `Particle` struct being byte-identical on the write (kernel) and read (draw) sides. `wgsl_reflect`'s package `main` is CommonJS inside a `"type": "module"` package, so `vitest.config.ts` aliases it to `wgsl_reflect.module.js` — without that alias the import fails with "exports is not defined". Kernel arithmetic is not covered there; it lives in `sim-uniform.test.ts` and the Rust pool tests it mirrors.
- `src/render-backends.test.ts` pins the `SceneRenderer` surface on *both* backend prototypes, because a capability gate means only one of them ever runs on a given machine and a lost method would otherwise surface on untested hardware. It cannot check for unexpected extra methods: TypeScript's `private` is erased, so internal helpers are own properties of the prototype.
- `crates/aether-core/src/engine/` is the orchestrator, split by domain: `mod.rs` holds the `Engine` struct, `new`, the subsystem accessors and the config/reset surface; `frame.rs` is `step` and the ambient drive; `perception.rs` the JS-writable input buffers and the four `push_*` calls; `output.rs` the dye/particle/debug buffers plus the tone-mapping table; `gpu.rs` the offload surface; `stats.rs` the `Stats` snapshot and `collect_stats`; `tests.rs` the engine-level tests. The child modules reach the struct's private fields because Rust privacy extends to descendant modules — so `encode_dye`/`collect_stats` are `pub(super)` only because `frame.rs` calls them across module lines, not because anything outside the engine may. Frame order in `frame.rs` is load-bearing and commented there; don't reorder it for tidiness.
- The WebGL2 compositor is split the same way as the WebGPU one, so a change to the look is made twice in mirrored places: `render/renderer.ts` owns the targets, the uploads and the scene/particle/overlay/composite draws, `render/bloom.ts` is the `BloomChain` (its own five ladder targets plus the down/up programs; `resize`, `record(scene, style)`, `output` for the composite — it draws fullscreen strips, so the caller binds `quadVao` first, which the overlay pass leaves changed), `render/luma-probe.ts` is the synchronous `readPixels` grid behind `sampleLuminance`, and `render/overlay.ts` is the `HandOverlay` mirroring the WebGPU one (its own VAO, dynamic vertex buffer and mesh scratch; `draw(program, target, hands, strength, pointScale)`, additive so the bloom catches the skeleton, and it leaves its VAO bound). Its construction-time halves mirror the WebGPU ones too: `render/programs.ts` (`createPrograms`/`disposePrograms` — every program as one record, from shader source plus the probed `ShaderEnv`) and `render/sources.ts` (`SceneSources`: the dye/debug/noise/camera textures, both uploads and the camera's own allocation state, so no video sizing is left in the renderer). Every one of those pieces dies and is rebuilt with the GL context, inside `Resources`.
- Two more DOM-free pieces are out of `hud.ts` and pinned by `hud-keys.test.ts`: `hud-keys.ts` (`hudAction` — the keydown → action map, including the two rules worth testing: a modified chord is never a shortcut, a key pressed inside an input belongs to the input, and Escape is claimed only while help is open; the HUD's `onKey` is now just a switch over the result) and `hud-status.ts` (`statusLine` — the perception line's heading/sub-line/tone, so the panel only diffs and writes it).
- `hud-cells.ts` is the telemetry grid as data (`statCells` → the exact string per `CELLS` id, `handsPresent`, `warpView` → label/fill/on), pinned by `hud-cells.test.ts`: every read is finite-guarded because `stats` is a raw WASM `Float32Array`, and `hud.ts` now just writes what comes back.
- The HUD's two pieces of non-DOM logic are out of `hud.ts` and unit-tested in `hud-readouts.test.ts`: `hud-frame-timer.ts` (`FrameTimer` — the peak-hold frame time and the rule that `stats.fps` is only an honest fallback after the warm-up, otherwise report nothing) and `hud-readouts.ts` (`presence`/`spellAt` slot inference, `fmtSmall`). Everything left in `hud.ts` touches the DOM.
- The entry is split by concern: `web/src/main.ts` is boot + the `window.__aether` test hooks only, `web/src/app.ts` is the `App` object and the frame loop, `web/src/engine-views.ts` owns every typed-array view over WASM memory (`rebuild` after any reallocating engine call, `refresh` once per frame), and `web/src/perception-pump.ts` owns the perception source's lifetime plus the duty-cycle cadence and the give-up rule.
- `gesture/` is split the same way: `mod.rs` (the module contract, every tuning constant, the `GestureTracker` struct, `new`, the accessors and `reset`), `kinds.rs` (`CannedGesture`/`Spell` with their names and hues — the only child that needs nothing from the parent), `state.rs` (`HandState`/`PoseState`/`TwoHandState`/`GestureConfig` and their defaults), then one file per ingest: `hands.rs` (`update_hands` + `drop_hand_frame`), `pose.rs` (`update_pose`), `two_hand.rs` (`update_two_hand`), over the existing `internals.rs`, `synth.rs` and `tests.rs`.
- `particles/` follows it too: `mod.rs` (the pool, its tuning constants, `new`, the offload/capacity accessors), `spawn.rs` (`seed_uniform`, `spawn_burst`, `spawn_ring`), `step.rs` (`step` plus the `lanes` split it is parallelised over), `forces.rs` (`impulse`/`damp`/`grip` — each one's offloaded path appends to the op log and returns), `render.rs` (the interleaved render buffer), over `lane.rs`, `offload.rs` and `tests.rs`.
- `flow.rs` and `mask.rs` are directories now, split the way the engine is — a child module reaches the struct's private fields, so a helper is `pub(super)` only where a sibling calls it. `flow/`: `mod.rs` (config, the constants every part reads, the `OpticalFlow` struct, `update`, pyramid allocation), `work.rs` (the reused per-level scratch), `pyramid.rs` (`build_pyramid`, `prolong`), `solve.rs` (`solve`/`finish`, `linearise`, `jacobi`, the border fade), `tests.rs`. `mask/`: `mod.rs` (config, constants, struct, accessors, `decay`/`reset`/`staleness`, the dt/EMA helpers), `stage.rs` (ingest + `process`), `edge.rs` (`rebuild_edge`), `tests.rs`. Those two use `use super::*` deliberately: each reads a dozen tuning constants, and naming them one by one meant editing an import list for every constant added.
- `bolt.rs`, `combo.rs` and `duet.rs` are directories now, each keeping recognition in `mod.rs` and moving the other half out: `bolt/` (`mod.rs` = the tuning constants, `Throw`/`ThrowTracker` and the detection in `update`; `fire.rs` = `fire` + `impact`, the streak and the detonation, effect only), `combo/` (`book.rs` = `ComboStep`/`ComboEffect`/`ComboDef` and the `COMBOS` table, data only), `duet/` (`book.rs` = `DuetEffect`/`DuetDef` and `DUETS` with the HUD's step wording). Each has its own `tests.rs`, and the books are re-exported from `mod.rs`, so `crate::combo::COMBOS` and friends keep their paths.
- `fluid/mod.rs` keeps the solver's contract (the tuning constants, the `Fluid` struct, `new`, the accessors, `reset`, `sanitize`) and `fluid/step.rs` holds `step` with the boundary work only it calls (`refresh_solid`, `enforce_boundaries`). The stage order in `step` is load-bearing and commented inline — don't reorder it for tidiness. `fluid/tests.rs` imports `Params` itself now, since `use super::*` no longer reaches it. `fluid/advect/` is split too: `mod.rs` is the stage on `Fluid` (the trace build, the RK2 integrate, the obstacle back-off, the body-contact dye fade) and `sampling.rs` is the DOM-free bilinear machinery it gathers through (`Stencil`, `TraceMap`, `Advector`'s MacCormack `run`, `corner_of`/`fetch`) — those items are `pub(in crate::fluid)` because `fluid/mod.rs` holds the `Advector` field.
- `crates/aether-wasm/src/` is split the way `engine/` is, and wasm-bindgen is happy with several `#[wasm_bindgen] impl AetherEngine` blocks across modules: `lib.rs` (the pointer-invalidation doc, the thread helpers, `STATS_LEN`, the struct, `new`, `layout`, `step`, config, `reset`, `start`, the binding tests), `buffers.rs` (the writable perception buffers, the `push_*` calls, the dye/particle/debug pointers), `gpu.rs` (offload plus the op-log protocol and the fluid/obstacle planes), `reports.rs` (stats, spell names, both spellbooks and their progress, practice mode, rush staging).
- `field.rs` and `spells/mod.rs` are split the same way. `field/`: `mod.rs` (the module doc and the two re-exports only), `grid.rs` (`Grid` — storage, indexing, sampling, splats, resampling, blur, the sanity scrubs), `vec_field.rs` (`VecField` over a pair of grids), `tests.rs`. `spells/`: `mod.rs` keeps the layer's contract — every tuning constant, `SpellReport`/`SpellState` and `apply`, which now reads as drive → one cast per hand → duets → time warp — and `cast.rs` is `cast_hand`, one hand's whole cast (the always-on palm drag, the per-spell field arithmetic, the release ring, the combo flash). The present/finite guard and the idle reset stay in `apply`'s loop, because only the loop can skip a slot.
- `web/src/styles.css` is an index of `@import`s only; the rules live in `web/src/styles/` (`base`, `hud/{panel,meters,spells,controls,perception}`, `hint`, `tutorial`, `help`, `focus`, `boot`, then `responsive`, `overdrive`, `spellbook`). The import order **is** the cascade order — it reproduces the order the single file was authored in, and the last three deliberately override the sections above, so moving an import changes which rule wins.
- `perception.ts` owns only the *session*: loading the two graphs, running them, the duty-cycle limiter and the give-up rule. The result shaping is `perception/packing.ts` (mirroring, sticky `HandSlots`, `packHands`/`packPose`, `MaskScaler`, `nextTimestamp` — pure, no MediaPipe, no DOM) and asset resolution is `perception/assets.ts` (model/runtime probes and the `INFO:` log muting). Mirroring stays in `packing.ts` alone: landmarks are flipped there and the mask is not, because `push_mask` mirrors itself.
- WebGPU types come from the `@webgpu/types` dev dependency, listed in `web/tsconfig.json`'s `types`. Views over WASM memory may be backed by a `SharedArrayBuffer` in the threaded build, which `GPUQueue.writeTexture` does not accept in the type definitions — those two call sites cast deliberately.
