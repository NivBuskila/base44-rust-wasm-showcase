# Base44 development notes

- This is browser-only: no API, database, or external credentials. Camera access needs browser permission; without it the app intentionally runs an animated ambient simulation.
- Base44 Compose builds the Rust/WASM from mounted source before starting Vite on host port 3000. The Node container deliberately has no Rust toolchain: its `npm run dev` skips the already-built artifact. Do not remove that WASM output while the web service is running; rebuild through the `wasm` service instead.
- `scripts/base44-wasm.sh` installs a cached wasm-pack, builds on each service start, and polls Rust sources/manifests for rebuilds. Build output, npm dependencies, vendored MediaPipe runtime, and downloaded models are generated/ignored, not committed.
- Two WASM builds: `web/src/wasm` (baseline) and `web/src/wasm-mt` (rayon + Web Workers, nightly `-Zbuild-std`, own target dir `target/wasm-mt`). The threaded link must export `__wasm_init_tls`/`__tls_*` explicitly (done in `scripts/build-wasm.sh`) or wasm-bindgen fails with "failed to find `__wasm_init_tls`". `scripts/base44-wasm.sh` is read once at container start — restart the `wasm` service after editing it.
- The preview proxy forwards `Cross-Origin-Opener-Policy` but strips `Cross-Origin-Embedder-Policy`, so Vite's headers alone never produce isolation. `web/public/coi-serviceworker.js` + `web/src/cross-origin-isolation.ts` re-attach both from a Service Worker and reload once; that runs only at top level, so the embedded iframe stays single-threaded by design. Verify the threaded engine in a standalone port-3000 tab (hard-reload once so the worker installs) via `window.__aether.diagnostics().engine`.
- MediaPipe inference runs in `web/src/perception.worker.ts` (module worker), driven by `ImageBitmap`s; `perception-worker-client.ts` is the `PerceptionSource` the app uses, with inline `MediaPipePerception` as fallback. Two non-obvious requirements: a module worker's inherited `importScripts` exists but throws, so `worker-import-scripts.ts` must override it via `Object.defineProperty` + indirect eval or the runtime fails with "ModuleFactory not set"; and Vite tags dynamic imports with `?import`, which its transform pipeline refuses for `public/` files — the `aether:mp-wasm-as-asset` plugin in `vite.config.ts` strips that query. A classic worker would avoid both but `worker.format` is per-project and the rayon threads need `es`.
- `web/src/performance-governor.ts` adapts quality at runtime from the smoothed fps: internal resolution (`Renderer.setQualityScale`), `pressure_iters`, then pool size. Tier 0 is the user's own settings, it is paused during overdrive, and HUD pool changes rebase it. Read `window.__aether.diagnostics().qualityTier`. The embedded preview iframe does run the loop and the governor whenever it is visible — and stops dead at `frames: 0` when it is hidden, which is why it can look like it never gets an animation frame — but always single-threaded (`SharedArrayBuffer unavailable`), so it settles at a degraded tier that says nothing about real performance — judge frame rate only in a standalone port-3000 tab.
- Vite uses polling and Compose passes the platform's `__VITE_ADDITIONAL_SERVER_ALLOWED_HOSTS` for rotating preview hosts. The CLI binds 0.0.0.0 without changing the normal localhost default.
- `crates/aether-core/src/visual.rs` measures the visual qualities tuning changes (dye saturation at the tone ceiling, structure/filament contrast, swirl, coverage, projection residual) from the dye grids, so a parameter change can be judged without a browser. `contrast` is normalised by brightness on purpose — it must stay a structure measure, not an exposure one — and `divergence` is an absolute residual that scales with drive strength, so compare it against `max_speed`, never a fixed number. Its tests pin `Params::default` against both failure modes: blown-out white frame and swirl-free flat field.
- `web/src/qa-recorder.ts` is how a manual QA pass leaves evidence: the frame loop feeds it diagnostics, it keeps a bounded summary (fps percentiles, step/render/inference/camera/hud times, quality-tier and perception transitions). It also records `engineReason` and `crossOriginIsolated`, so a `single:1` session says which gate rejected the threaded build instead of leaving it to guesswork. `frameMs` is the whole callback and `outsideMs` is the wall-clock gap it did not spend, which is the row that matters when the measured work sums far under the frame period: that time is GPU work completing after the GL calls return, compositing, or another task holding the loop.
- Reading a QA session from outside the tab goes over HTTP, not storage: `curl localhost:3000/__qa/session`, served by the `aether:qa-session-endpoint` plugin (`web/qa-session-endpoint.ts`), which holds the newest posted record in dev-server memory. `localStorage` is **not** a usable bridge — Chrome partitions it by top-level site, so the embedded preview iframe gets its own bucket and can never read a standalone tab's record even though the origin is identical; a whole debugging round was lost to reading the iframe's own numbers back and believing they were the user's. The recorder still writes storage for in-tab reads (`window.__aether.lastQaSession()`) and `sendBeacon`s the same summary to the endpoint, and it uploads/persists only from a top-level document so the iframe's own throttled single-threaded record cannot overwrite a real session.
- Verify with `docker compose -f docker-compose.base44.yml ps`, `curl -f http://localhost:3000/`, `docker compose -f docker-compose.base44.yml exec -T wasm cargo test --workspace`, and `docker compose -f docker-compose.base44.yml exec -T web npm run typecheck`.
- Browser readiness: `#boot.done` is intentionally invisible, so wait for attachment, not visibility. Read `window.__aether.diagnostics()` for advancing frames and camera/perception status. A canvas screenshot confirms actual rendering; a populated DOM alone does not.
- Initial setup verified native workspace tests, TypeScript checking, live source serving, and the preview rendering in ambient mode. Real webcam gesture recognition requires camera permission and was not verified during setup.
- An open palm is two spells: it latches `Repel`, and after `SCULPT_DWELL` (0.5 s) of holding still it becomes `Sculpt` (particles gather onto the hand skeleton); sweeping it again returns to `Repel`. So a `holding()` open palm in `spells.rs` tests is a sculpt — use `latched()` for a steady repel. `Beam` (both hands `Ignite`) and `Release` (opening a fist held ≥ `RELEASE_MIN_CHARGE`) are reported by `spells.rs` only and are never latched by the tracker.
- Gesture latency has two ceilings that look like nothing from the outside. MediaPipe's duty-cycle limiter in `perception.ts` (`BUDGET_MS`/`MAX_DUTY`) exists only to keep a synchronous inference from stalling the render loop, so `perception.worker.ts` constructs it with `rationInference: false` — left on there it inserts idle time between landmarks (~16 Hz down to ~6 Hz at a 60 ms pass) while blocking nobody. And the camera is opened with `frameRate: { ideal: 60 }`: perception submits a frame only when `video.currentTime` advances, so the capture rate is a hard floor on how soon a gesture can be seen, however fast inference is.
